## 技术选项规范
- **不随意添加依赖** 添加依赖前必须进行严谨的判断（已有依赖能不能完成工作，功能点价值是否值得添加一个依赖，依赖添加后会不会还有后续功能可以用到）
- **选型优先级**事实行业标准>大型社区/基金会开源>国际大厂开源>国内大厂开源>知名个人开源。不得采用来路不明依赖
- **选型活跃度**必须是活跃项目，迭代快速，问题解决及时。停止维护的项目禁止采用

## 包管理规范
先检测工作目录使用什么包管理工具，以已有的为先。如果没有则优先采用uv进行包管理

## 代码风格与格式规范
优先满足本层中的列出的规则，如果本层中没有指定则以Google Python Style Guide和clean code作为兜底标准

### 基本原则
- **单一职责 (SRP)**: 每个类、模块、函数仅应有一个变更理由。严禁在单个函数中混合"验证、持久化、通知"等不同维度的逻辑
- **DRY (Don't Repeat Yourself)**: 发现重复逻辑必须立即提取为通用工具函数或基类方法，禁止复制粘贴
- **KISS (Keep It Simple)**: 优先选择最简单、最直观的解决方案。拒绝过度设计、不必要的抽象层
- **高内聚低耦合**: 模块间依赖应最小化，通过接口或清晰的数据结构交互

### 函数设计规范
- **参数限制**: 函数参数数量严禁超过 3 个。若需更多参数，必须封装为对象
- **纯函数优先**: 尽可能编写无副作用的纯函数。若必须产生副作用，需在命名或文档中明确标识
- **粒度控制**: 单个函数逻辑行数建议控制在 50 行以内。超出时，必须评估是否可拆分
- **早期返回**: 优先使用"卫语句"处理异常或边界情况，减少嵌套层级

### 代码可读性
- **意图导向**: 代码结构应直接反映业务意图，而非实现细节
- **自解释代码**: 变量和函数命名应足够清晰，减少对注释的依赖
- **注释原则**: 注释仅用于解释"为什么"，而非"做什么"

### 工具优先
对于以下场景，优先使用指定的库进行处理，如果没有安装则让用户自行选择安装该库还是自行实现
- 对于日期操作，优先使用python-dateutil代替自己写逻辑
- 对于集合操作，优先使用more-itertools代替自己写逻辑
- 对于数据验证/序列化操作，优先使用pydantic（V2版本）代替自己写逻辑
- 对于非固定格式的json（无schema）操作，优先使用orjson代替自己写逻辑

### 类型安全规范
禁止省略类型注解。所有变量，函数的返回值/入参等即使能都自动推导出来也必须要有类型注解

### 文档注释规范
- **所有注释必须使用中文**
- 所有公共模块、类、函数必须有 **Google 风格 Docstring**
- **禁止行尾注释** - 必须在代码上方单独一行
- 核心逻辑必须要有行注释
- 注释与前面代码必须保留 **1 个空白行**

## 安全规范

### 资源安全
- 所有的资源使用完成以后必须关闭，优先使用with语句处理资源
- 所有资源应该在哪开启在哪关闭，不得在中间过程的函数调用中关闭。一旦函数调用层级过多。将难以排除资源是否被关闭

## 静态代码检查
任务完成之后必须执行静态检查脚本。
- ruff代码格式化
```bash
uv run ruff format .
```
- ruff代码语法检查
```bash
uv run ruff check --fix .
```
- pyright代码语法检查
```bash
uv run pyright
```
**验证标准**：所有检查通过无错误，无警告
